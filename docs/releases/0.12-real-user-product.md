# BandWagon 0.12 - Real User Product

This release moves BandWagon from admin/development tooling into the first complete user-facing product flow.

## 014 - Authentication and Sessions

- Passwordless email or mobile-number sign-in
- Six-digit OTP verification
- New-account creation through the same OTP flow
- Pre-provisioned contacts can verify themselves on first sign-in
- HTTP-only, same-site session cookie
- Server-side revocable sessions
- 30-day session lifetime
- OTP expiration and attempt limits
- Per-identifier request throttling
- Authentication event history
- Phone identifiers remain encrypted/hashed using the existing privacy utilities
- Email OTP uses SMTP2GO
- Mobile OTP uses the existing Twilio Messaging Service

`AUTH_SECRET` is recommended. If it is not set, authentication hashing falls back to the existing stable `DATA_ENCRYPTION_KEY`.

Optional development-only setting:

```text
AUTH_DEBUG_OTP=true
```

Do not enable `AUTH_DEBUG_OTP` in production.

## 015 - Household and Organization Onboarding

Authenticated adults receive a household automatically when creating an account.

The user-facing onboarding flow can:

- Add students to the household
- Create explicit guardian relationships
- Keep guardian approval enabled by default
- Join an organization using an existing BandWagon join code
- Add managed students to an organization
- Configure the signed-in adult as a driver
- Record organization join history

## 016 - User Ride Product

New user-facing screens:

```text
/login
/app
/app/rides
/app/household
/app/driver
```

The product API is session-authenticated and does not use `ADMIN_TEST_TOKEN`.

### Parent / Guardian

- See managed household riders
- Add students
- Join organizations
- See upcoming normalized events
- Request rides for self or managed students
- Enter pickup/drop-off addresses when needed
- Review driver offers
- Accept an offer
- Track confirmed rides
- View the correct assigned rider location even when the student is a secondary passenger in a pooled carpool

### Student

Existing student accounts with a configured contact and `user_account` can verify that contact and sign in through the same OTP flow. Guardian-managed students continue to be represented inside the parent/guardian household.

### Driver

- Opt in or pause driving
- Set available seat count
- Add a simple vehicle label/color
- Browse open ride requests in joined organizations
- See only generalized pickup-area information before a match
- Offer a ride
- Access exact assigned pickup/drop-off information only after authorization allows it
- Move an accepted ride through the existing ride lifecycle

### Matching

Creating an open user ride request refreshes smart-match suggestions automatically. Suggestions stay human-in-the-loop. No driver or passenger is silently assigned.

## Privacy

This release uses the location privacy layer end-to-end:

- User-entered addresses are geocoded server-side using the existing Google Maps server key.
- Formatted exact addresses and exact coordinates are stored encrypted using `DATA_ENCRYPTION_KEY`.
- Only generalized city/area information is used for pre-match discovery and smart matching.
- Open ride listings never expose the exact address.
- Exact-location reveal continues to use the authorization-aware service from migration 010 and is audit logged.
- Pooled secondary riders resolve to their own assigned pickup/drop-off rather than another household's primary location.


## Required delivery configuration

Recommended authentication secret, Runtime only:

```text
AUTH_SECRET
```

Existing `DATA_ENCRYPTION_KEY` must remain stable.

For email OTP:

```text
SMTP2GO_API_KEY
EMAIL_FROM
```

For mobile OTP, the existing Twilio variables are used:

```text
TWILIO_ACCOUNT_SID
TWILIO_AUTH_TOKEN
TWILIO_MESSAGING_SERVICE_SID
TWILIO_PHONE_NUMBER
```

`TWILIO_PHONE_NUMBER` is not required by the automatic Messaging Service path, but remains used elsewhere when SMS is explicitly forced.

User-entered addresses use the existing:

```text
GOOGLE_MAPS_SERVER_API_KEY
```

## Suggested smoke test

1. Open `/login` in a private browser window.
2. Enter a new email address and provide a name when prompted.
3. Receive and verify the OTP.
4. Confirm redirect to `/app`.
5. Open Household and add a student.
6. Enter a FloMoGo organization join code.
7. Add the student to FloMoGo.
8. Open Driver and opt the adult into driving.
9. Open Rides and create a ride request for the student against an upcoming event, including a pickup address.
10. Confirm the open driver view shows only the generalized area.
11. From a second test account, offer the ride.
12. From the first account, accept the offer.
13. Confirm the matched driver can reveal the authorized exact pickup location.
14. Confirm the matched ride can progress through the ride lifecycle.
15. Sign out and confirm the session is revoked.
