# BandWagon 0.12.1 - Multi-Organization Hardening

This patch makes multi-organization membership a first-class production boundary after the 0.12 user product release.

## Membership model

- A household is global to the BandWagon account.
- Every person has independent organization memberships.
- A parent joining an organization does not automatically enroll every student.
- Adding a new student to a household no longer copies the parent's organizations.
- Household managers explicitly add each student to each organization.
- Top-level person + organization membership is now unique at the database layer.
- `membership_source` records new join-code and guardian-added memberships.

Existing memberships created before this migration are preserved. BandWagon cannot safely infer whether a pre-017 student membership was intentionally added or inherited by the earlier 0.12 behavior, so the migration does not delete existing student memberships.

## Driver model

Vehicle identity remains person-level, but participation is now organization-specific through `driver_organization_settings`.

Each organization can independently define:

- active / paused / blocked
- seat capacity
- always-willing behavior
- multi-passenger preference
- detour tolerance
- pickup radius

A driver who belongs to only one organization is safely backfilled from the old profile. If an existing driver belongs to multiple organizations, every organization is migrated to **paused** (unless globally blocked) so BandWagon never assumes consent to drive for every group.

Driver schedule conflicts are checked across **all organizations** because a person cannot physically drive two organization rides at the same time.

## Tenant boundary

The central platform remains a cross-organization personal dashboard:

```text
bandwagon.harrisonward.net
```

When a request arrives through a verified organization hostname, authenticated product and onboarding APIs are scoped to that organization:

```text
flomogo.harrisonward.org -> FloMoGo only
rides.customer.org       -> that customer only
```

This applies to organization lists, events, ride requests, rides, driver actions, match refreshes, location reveal, join codes, student organization enrollment, and driver configuration.

## Ride safety

Ride creation already validated both requester and passenger membership in the selected organization. 0.12.1 keeps that control and additionally requires organization-specific driver opt-in when offering or accepting a ride.

Pooling and smart matching now read organization-specific driver preferences rather than the old global driver state.

## Deployment

After merge and deploy:

```bash
npm run db:migrate
```

Expected:

```text
Applied 017_multi_org_hardening.sql
```

## Suggested smoke test

1. Create or use two organizations.
2. Join the same adult to both.
3. Add a new student and verify the student joins neither organization automatically.
4. Explicitly add the student to only Organization A.
5. Verify an Organization B ride request cannot be created for that student.
6. Enable the adult as a driver in Organization A only.
7. Verify Organization B does not show the adult as an available driver.
8. Enable the adult in Organization B with a different seat capacity and confirm each org retains its own setting.
9. Create a confirmed ride in Organization A and verify overlapping smart matching in Organization B excludes the same driver.
10. On the central platform, verify both organizations are visible.
11. On an organization custom/default hostname, verify only that organization's data is returned.
