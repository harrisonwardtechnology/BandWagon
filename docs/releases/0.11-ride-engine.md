# BandWagon 0.11 - Ride Engine Complete

This release combines roadmap phases 011, 012, and 013 into one deployable release while preserving separate migrations and service boundaries.

## 011 - Driver Experience

Driver profiles now support:

- Seat capacity
- Active / paused / blocked status
- Default willingness to help
- Multi-passenger preference
- Vehicle label, make, model, color, and optional plate hint
- Maximum detour time
- Maximum pickup radius
- Organization-specific preferred service zones using generalized coordinates only
- Weekly recurring availability
- One-day availability exceptions

Service zones intentionally use generalized coordinates. The matching engine does not need or read a driver's exact home address.

## 012 - Multi-Passenger Carpooling

A confirmed ride can now carry multiple compatible ride requests.

The pooling layer provides:

- Capacity snapshot when the ride is created
- Live seat accounting
- One assignment record per ride request
- Multiple passengers per ride
- Pickup/drop-off stop records
- Automatic primary-request stop creation
- Pickup-first / drop-off-second stop resequencing when passengers are added
- Compatibility checks for organization, event, direction, pickup time, and seat capacity
- Transaction locks to prevent overbooking
- Passenger manifest and remaining-seat calculation
- Ability to remove and later reassign a secondary request before departure
- Automatic assignment/request lifecycle sync when a ride completes, cancels, or becomes a no-show

The original request remains the ride's primary request for backward compatibility. Additional requests are represented through `ride_request_assignments`.

## 013 - Smart Matching

Smart matching creates ranked suggestions, not automatic assignments.

### Driver candidate factors

- Driver opted in through recurring availability or `willing_by_default`
- Enough seats
- No conflicting confirmed/in-progress ride near the requested pickup time
- Preferred service-zone fit
- Distance from generalized pickup area to generalized driver service zone
- Multi-passenger capability

### Existing-carpool candidate factors

- Same organization
- Same event
- Same ride direction
- Ride has not departed
- Pooling enabled
- Enough remaining seats
- Pickup time within configured tolerance
- Generalized pickup areas within the driver's configured radius

### Human-in-the-loop rule

A high score is only a suggestion. BandWagon does not silently assign a driver or move a passenger into another family's carpool.

The admin development API has a direct attach action for exercising the pooling engine. The production user workflow should present suggestions/offers for confirmation before calling that low-level operation.

## Privacy

Matching uses `private_locations.generalized_area`, `generalized_latitude`, and `generalized_longitude` only. It does not decrypt exact addresses.

Exact pickup/drop-off reveal continues to be controlled by the location privacy service added in migration 010.

## Notification Cost Control

Suggested drivers can be notified using the existing `new_ride_available` notification policy. That policy remains push-first, avoiding an SMS blast for routine ride opportunities.

## Configuration

Optional environment settings:

```text
MAX_POOL_TIME_GAP_MINUTES=45
DRIVER_CONFLICT_WINDOW_MINUTES=120
```

`MAX_POOL_TIME_GAP_MINUTES` controls the global maximum pickup-time difference for pooling. A driver's `max_detour_minutes` may reduce that further.

`DRIVER_CONFLICT_WINDOW_MINUTES` prevents the matching engine from suggesting a driver for a new standalone ride when that driver already has another active ride near the same time. Existing compatible carpools are ranked separately instead.

## Deployment

After merging and deploying the release, run:

```bash
npm run db:migrate
```

Expected new migrations:

```text
Applied 011_driver_experience.sql
Applied 012_multi_passenger.sql
Applied 013_smart_matching.sql
```

Then open:

```text
/admin/ride-engine
```

Suggested smoke test:

1. Select FloMoGo.
2. Configure two driver profiles.
3. Add a generalized service zone and recurring availability to at least one driver.
4. Create/open a ride request using the existing `/admin/rides` workflow.
5. Generate smart matches in `/admin/ride-engine`.
6. Create/confirm one ride using `/admin/rides`.
7. Create a second compatible request.
8. Generate matches and confirm the existing ride appears as a carpool candidate.
9. Use the development pooling action to add the second passenger.
10. Verify seat totals, passenger manifest, and pickup-before-drop-off stop ordering.
